Visual Tournament 축 연결 판단

축을 먼저 연결할 것인가, 민감도를 먼저 잴 것인가?

선택 계층은 실제로 동작하지만 축이 렌더러에 연결되지 않아 후보 8개가 모두 같은 증거로 채점된다. 지금 연결할지, 먼저 artifact CSS의 옛 매핑을 정리할지 정해야 한다.

  • 후보 생성·채점·승자 선택은 동작하고 테스트로 고정돼 있다
  • 축 4개가 연결되지 않아 후보를 바꿔도 렌더 결과가 같다
  • artifact CSS가 아직 옛 4테마 매핑이라 축을 지금 얹으면 두 번 고치게 된다

후보 축 4개를 스타일시트로 내려서 Visual Tournament를 실제 비교로 만들 것인가?

density / measure / figurePlacement / typeScale 네 축이 후보 객체에는 있지만 렌더러가 읽지 않는다. 그래서 후보 8개가 전부 동일한 HTML을 만들고 동일한 증거로 채점된다. 선택 계층은 진짜고, 비교 대상이 가짜다.

오늘 결정할 것

  1. 축을 지금 연결할 것인가, 아니면 artifact CSS 정리 뒤로 미룰 것인가
  2. 네 축을 한 번에 연결할 것인가, 하나씩 할 것인가
  3. 연결 전까지 CLI 출력에서 tournament를 감출 것인가

아직 모르는 것

  • 축 조합이 실제로 채점을 갈라놓을 만큼 렌더를 바꾸는지 아직 측정하지 않았다
  • artifact CSS 정리 범위가 얼마나 큰지 산정되지 않았다
  • 후보 8개를 각각 렌더하면 build 시간이 얼마나 늘어나는지 모른다

가장 강한 반론

축이 채점을 갈라놓는다는 것을 아무도 확인하지 않았다. 네 축을 연결한 뒤에도 점수가 거의 같게 나오면, 우리는 build 시간을 8배로 늘리고 얻은 것이 없게 된다. 순서가 틀렸다. 먼저 두 후보를 손으로 렌더해서 점수가 갈리는지 재고, 갈릴 때만 연결하는 것이 맞다.

검증되지 않은 가정

  • 채점 함수가 축 변화에 민감하다
  • 후보 8개를 각각 렌더해도 build 시간이 감당 가능하다
  • artifact CSS를 나중에 정리해도 축 연결이 그대로 살아남는다

무엇이 이걸 틀리게 만드나

  • 네 축을 연결했는데 후보 간 점수 차가 측정 잡음보다 작다
  • 후보별 렌더 때문에 build가 지금의 몇 배로 늘어 CI에서 쓸 수 없게 된다
  • artifact CSS 정리가 축 연결부를 전부 다시 쓰게 만든다

결정을 뒤집을 조건

  • 손으로 만든 두 후보의 점수 차가 3점 미만이면 연결을 접고 tournament를 CLI에서 감춘다
  • artifact CSS 정리 산정이 축 연결의 두 배를 넘으면 순서를 바꾼다
  • 후보 생성과 채점src/qa/candidates.ts
