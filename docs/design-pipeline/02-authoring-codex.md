# 2단계 조사: `DESIGN.md`와 `SOUL.md`를 더 신뢰성 있게 만드는 법

## 결론

녹음은 좋은 **수집 매체**지만, 그 자체가 좋은 철학 작성법은 아니다. 말로 한
설명을 바로 요약해 `SOUL.md`로 만드는 방식은 참여자가 이미 자기 취향을 알고,
그 이유를 정확히 말할 수 있으며, 말한 원칙이 실제 선택과 일치한다는 세 가정을
동시에 둔다. 이 가정들은 자주 깨진다. 녹취는 증거 중 하나로 보존하되, 최종
문서는 **기존 행동의 증거 + 구체적 시안의 강제 선택 + 반례 + 구조화 인터뷰**를
교차 확인해 만들어야 한다.

권고 우선순위는 다음과 같다.

1. **기본 프로토콜은 “증거 수집 → A/B 강제 선택 → 이유 확인 → 반례 확인 →
   문서화 → 보류 시안으로 검증”으로 한다.** 자유 대화나 녹음은 이 프로토콜의
   인터뷰 구간에만 넣는다. 이미 만든 제품·문서가 있다면 말보다 그것을 먼저
   본다.
2. **역할을 분리한다.** `.forma/SOUL.md`는 제품이 누구를 위해 어떤 판단을
   우선하는지 기록하는 느리게 변하는 제품 철학이고, `.forma/DESIGN.md`는 그
   철학을 시각적으로 구현하는 원칙·토큰 의미·용례·금지 패턴을 기록하는 시각
   언어다. Forma 저장소 루트 `DESIGN.md`는 renderer 자체의 설계 시스템이므로
   그대로 둔다.
3. **산문을 곧바로 renderer 입력으로 쓰지 않는다.** 두 Markdown은 사람과
   에이전트를 위한 근거 문서다. 향후 문서별 스타일 통로를 만들 때는 승인된
   시각 결정을 별도의 스키마 검증 가능한 토큰/프로필로 컴파일하고, 최종 spec에
   버전 또는 값으로 고정해야 한다. 이것은 1단계에서 확정된 “저작 시점 어댑터”의
   문서 저작 측 절반이다.
4. **“잘 썼다”는 단일 자동 점수는 만들지 않는다.** 구조·모순·근거 연결은
   lint할 수 있고, 보류한 A/B 선택을 예측하는지는 실험할 수 있다. 그러나
   취향의 정당성이나 제품 철학의 진실을 자동으로 증명할 수는 없다. 문서가
   소유자의 선택을 재현하는지와 목표 사용자의 결과를 개선하는지는 별도 검사다.

이 결론은 1단계의 확정 사항을 다시 열지 않는다. 최종 HTML/CSS/셰이더 직접
생성, paper.design 셰이더, 산출물 내 무드보드 이미지는 제외한다. 현재의 실제
기술 병목도 그대로다. `buildStylesheet`의 문서별 입력은 폰트뿐이고,
`artifactCss()`와 `blockCss()`에는 인자가 없어, 아래 문서를 잘 만들어도 지금은
시각 결정이 renderer로 내려갈 통로가 없다.

## 조사 범위와 사실 표기

- **[확인]** 저장소 파일이나 링크한 원문을 직접 읽고 확인한 내용이다.
- **[제안]** Forma에 적용하기 위한 설계 판단이다.
- **[추론]** 확인된 자료에서 도출했지만 직접 검증하지 않은 판단이다.
- **[미확인]** 이번 조사로 확인하지 못한 내용이다.

웹 자료는 2026-08-03에 확인했다. DTCG 2025.10 보고서는 안정된 Candidate

이를 “표준”이라고 뭉뚱그리지 않는다.

## 1단계 조사에서 합의된 것과 갈린 것

### 합의

- **[확인]** 두 1단계 조사 모두 원본 영상의 자유 HTML 생성 계약을 Forma의
  최종 산출물 계약에 그대로 넣을 수 없다고 봤다.
- **[확인]** 둘 다 사람의 철학/무드 입력을 제한된 토큰·블록·composition 축으로
  번역하는 저작 시점 어댑터가 가능하다고 봤다.
- **[확인]** 둘 다 현재 후보 선별기가 깨끗한 후보의 취향 차이를 구분하지 못하며,
  사람의 평가 루프가 필요하다고 봤다.
- **[확인]** 둘 다 Forma 루트 `DESIGN.md`가 이미 renderer의 시각 언어 원천이라
  사용자 프로젝트의 동명 파일과 충돌한다고 지적했다.
- **[확인]** 둘 다 제품 철학을 renderer가 직접 해석하게 두지 않고 에이전트의
  저작 입력으로 사용해야 한다고 봤다.

### 갈린 지점과 이번 판단

| 쟁점 | 1단계 codex | 1단계 claude | 이번 판단 |
|---|---|---|---|
| 저작용 자유 HTML | 별도 sidecar 선택지로 남김 | 축 확장 후 필요성을 측정해 조건부 검토 | 과제의 확정 사항대로 폐기 |
| 사용자 시각 문서 형식 | 프로젝트 수준 `DESIGN.md`를 유지하는 쪽 | `forma.mood.json`으로 이름·형식 변경 | 사람용 `.forma/DESIGN.md`와 기계용 토큰 프로필을 분리 |
| 파일 스코프 | 프로젝트당 하나 | 프로젝트당 하나 | 제품/브랜드 프로젝트당 하나, 문서별 override는 별도 명시 필드로만 허용 |
| 선별 입력 | 별점·pairwise·코멘트 병행 | 구조화 질문을 우선하고 자유 코멘트는 보조 | pairwise + 이유 코드 + 선택적 자유 설명을 우선 |

이번 조사는 “Markdown이냐 JSON이냐”를 양자택일하지 않는다. 기존 사례를 보면
철학·원칙 문서와 실행 가능한 값은 서로 다른 산출물이다. Markdown은 판단 근거와
반례를 보존하고, JSON/TypeScript 토큰은 모호하지 않은 값을 전달한다. 둘을 한
파일에 억지로 합치면 사람에게는 읽기 어렵고 renderer에는 모호해진다.

## 1. 선행 사례: 이미 있는 산출물은 문제를 어떻게 나누는가

### 비교표

| 선행 산출물 | 주로 담는 것 | 의도적으로 담지 않는 것 | Forma가 가져올 부분 |
|---|---|---|---|
| creative/brand brief | 프로젝트 목표, 배경, 대상, 메시지, 산출물, 제약, 일정, 책임자 | 완성된 시각 해법과 세부 토큰 | `SOUL.md`의 입력 질문, 소유자·대상·성공 조건·비목표 |
| design principles | 반복되는 판단을 위한 짧은 원칙과 점검 질문 | 색상값·컴포넌트 구현 세부 | 두 문서의 각 원칙을 실제 결정에 적용 가능한 문장으로 쓰는 법 |
| art direction / brand guide | 사진·색·타이포·구도·후처리의 좋은/나쁜 예와 사용 맥락 | 제품 전략 전체와 사용자 문제의 우선순위 | `DESIGN.md`의 구체 예, 반례, “언제/왜” 규칙 |
| design tokens | 이름, 값, 타입, alias, group, description 등 교환 가능한 데이터 | 브랜드 목적, 감정, 좋은 결과의 이유 | 승인된 시각 결정을 기계 입력으로 내리는 별도 계층 |
| `AGENTS.md` / `CLAUDE.md` / rules | 에이전트가 반복해서 따라야 할 명확한 규칙, 명령, 범위와 우선순위 | 취향 발견 과정, 암묵적 미감, 강제 집행 | 짧고 구체적인 문장, 스코프, 우선순위, 검증 절차 |

### 1-1. Creative/brand brief는 철학 발견의 출발점이지 시각 시스템이 아니다

**[확인]** Adobe의 creative brief 안내는 brief를 프로젝트 범위와 목표를
정의하는 문서로 설명하며, 프로젝트 배경·목표, 대상 독자, 핵심 메시지,
deliverable, 일정·예산, 이해관계자와 책임을 포함한다. 또한 brief는 구체적인
concept을 미리 정하는 문서가 아니라 탐색할 경계를 제공해야 하며, 고객에게
혼자 양식을 채우게 하기보다 초기 회의에서 함께 작성하라고 권한다
([Adobe creative brief](https://business.adobe.com/blog/basics/creative-brief)).
같은 회사의 brand brief 예시는 더 지속적인 층을 따로 둔다. 브랜드가 하는 일과
대상, 핵심 가치, personality, 경쟁 맥락을 먼저 적고 시각 작업을 시작하라고
한다
([Adobe brand brief example](https://www.adobe.com/express/learn/blog/how-to-design-a-logo)).

**[적용]** `SOUL.md`도 “우리는 대담하다” 같은 형용사 목록으로 시작하지 말고,
다음 사실에서 출발해야 한다.

- 누가 이 제품/문서를 어떤 상황에서 쓰는가
- 사용 전후에 무엇이 달라져야 하는가
- 무엇을 최적화하고 무엇을 희생할 수 있는가
- 성공과 실패를 무엇으로 관찰할 수 있는가
- 누가 최종 취향 결정권자이고 누가 영향받는가

**[한계]** brief는 한 프로젝트의 목표와 납품 경계를 맞추는 데 강하지만,
여러 문서에 걸쳐 재사용할 시각 문법이나 기계가 읽을 토큰을 정의하지 않는다.
따라서 brief 전체를 `SOUL.md`로 복사하면 일정·예산 같은 일회성 정보가 영구
컨텍스트를 오염시킨다.

### 1-2. Design principles는 “평가 렌즈”다

**[확인]** GOV.UK 원칙은 “사용자 필요에서 시작”, “데이터로 설계”, “반복”처럼
구현보다 판단 방향을 제시한다
([Government Design Principles](https://www.gov.uk/guidance/government-design-principles)).
USWDS는 원칙을 팀이 공통 목표에 정렬하고 설계·구현 결정을 평가하는 렌즈라고
명시하며, 각 원칙 아래 실제 점검 질문을 둔다
([USWDS Design Principles](https://designsystem.digital.gov/design-principles/)).

**[적용]** 두 Forma 문서의 원칙도 다음 형태여야 한다.

> 원칙 → 이 원칙이 필요한 이유 → 선택 상황에서의 판정 규칙 → 좋은 예/반례

예를 들어 “차분하다”는 원칙이 아니다. “운영 중 이상 신호가 먼저 보이도록
장식 대비보다 상태 대비에 색을 쓴다”는 선택 규칙이다. `DESIGN.md`의 현재 문장
“theme differences come from composition, rhythm, and typography rather than
ornamental effects”는 이 형식에 가깝다.

**[한계]** 원칙은 값과 구현을 주지 않는다. “일관되되 획일적이지 않게” 같은
좋은 원칙도 두 후보 중 무엇을 고를지 충분히 구체적이지 않을 수 있다. 그래서
예시와 토큰 계층이 필요하다.

### 1-3. Art direction 문서는 말과 실제 이미지를 연결한다

**[확인]** Docusign의 공식 사진 가이드는 “Connected, Natural, Inspired”라는
방향만 제시하지 않는다. 실제 주제, 배경, depth of field, 채도·온도·대비,
금지하는 회색/washed 처리, 마스크를 써야 하는 맥락과 초점부를 자르지 말라는
구체 규칙까지 둔다
([Docusign Photography](https://brand.docusign.com/photography)). Adobe의 brand
guide 안내도 로고, 타이포그래피, 색, 이미지 사용 규칙과 do/don't를 시각
정체성의 실행 계층으로 분류한다
([Adobe brand style guide](https://www.adobe.com/creativecloud/business/teams/resources/how-to/brand-guide.html)).

**[적용]** `.forma/DESIGN.md`는 형용사와 hex 값 사이의 빈칸을 채워야 한다.
구체적으로 다음을 포함한다.

- 정보 위계, 밀도, 읽기 리듬, 표면 깊이, 강조와 상태 색의 용도
- light/dark 및 접근성 불변 조건
- 권장 예와 금지 예, 각각의 이유
- “항상/보통/예외적으로”를 구분한 적용 강도
- artifact에 따라 달라질 수 있는 것과 모든 artifact가 공유하는 것

**[한계]** 브랜드 art direction은 마케팅 이미지의 인상에 강하지만, 데이터
정확성·문서 정보 구조·접근성·오프라인 계약을 자동으로 보장하지 않는다.
Forma에서는 기존 hard gate가 언제나 취향보다 우선한다.

### 1-4. Design token 표준은 철학의 대체물이 아니라 전달 형식이다

**[확인]** DTCG Format Module 2025.10은 디자인 토큰을 도구·기술 사이에서
공유할 수 있는 플랫폼 독립적인 디자인 결정 표현으로 설명한다. 파일은 JSON이며,
token은 최소 name/value를 갖고 type, description, extension, deprecation,
group, alias 등을 표현할 수 있다
([DTCG Format Module 2025.10](https://www.designtokens.org/tr/2025.10/format/)).
상위 보고서는 색, 간격, 타이포 스케일을 토큰의 예로 들며, 해당 보고서가
W3C Standard가 아니라고 명시한다
([DTCG reports 2025.10](https://www.designtokens.org/tr/2025.10/)).

**[확인]** 현재 Forma도 `src/design/tokens.ts`에 색·간격·radius·breakpoint·
motion·measure 값을 두고 `foundations-css.ts`에서 semantic CSS custom property로
방출한다. 그러나 palette와 token set은 전역 상수이고, 문서별 입력이 아니다.

**[적용]** `DESIGN.md`에는 “왜 accent가 존재하고 어디에 쓰는가”를 쓰고,
향후 기계용 프로필에는 `accent`의 실제 값과 type을 쓴다. 토큰 description은
짧은 사용 목적을 담을 수 있지만, 선택의 역사·반례·제품 철학까지 떠맡기면
안 된다.

### 1-5. Agent context 파일은 발견된 철학을 전달하는 법을 보여준다

**[확인]** AGENTS.md 관행은 README와 분리해 build/test 명령, 코드 스타일,
테스트, 보안 같은 에이전트용 지시를 두며, 가까운 경로의 파일이 우선하는
스코프 모델을 쓴다
([AGENTS.md](https://agents.md/)). Codex 공식 문서는 전역에서 프로젝트·하위
디렉터리로 지침을 합치고 가까운 지침이 우선한다고 설명한다
([Codex AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)).
Claude Code 공식 문서도 `CLAUDE.md`에 build 명령, 규약, 구조, workflow처럼
매 세션 필요한 구체 사실을 두고, 다단계 절차는 skill이나 path-scoped rule로
옮기며, 짧고 구체적일수록 더 일관되게 따른다고 설명한다
([Claude Code memory](https://code.claude.com/docs/en/memory)). 두 제품 모두
이 파일을 강제 집행 장치가 아니라 모델 컨텍스트로 본다.

**[적용]** `SOUL.md`와 `DESIGN.md`도 다음을 지켜야 한다.

- 선언보다 관찰 가능한 명령을 쓴다.
- 범위와 우선순위를 명시한다.
- 충돌 규칙을 둔다. 예: 접근성/정확성 > 제품 철학 > 시각 선호.
- 에이전트가 코드에서 쉽게 알 수 있는 사실을 반복하지 않는다.
- 긴 elicitation 기록은 부록이나 별도 evidence log에 두고 핵심 문서는 짧게
  유지한다.

**[한계]** `AGENTS.md`류는 이미 결정된 규칙을 전달하는 형식이지, 취향을
발견하는 방법이 아니다. 이를 본떠 문장을 깔끔하게 쓰는 것만으로 잘못 추출한
철학이 옳아지지는 않는다.

## 2. 녹음-정제 방식은 어디서 실패하는가

### 2-1. 말한 이유와 실제 선택의 이유가 다를 수 있다

**[확인]** Nisbett와 Wilson의 고전적 검토는 사람이 고차 인지 과정에 직접
접근하지 못하고, 자신의 반응 이유를 그럴듯한 사전 인과 이론으로 보고할 수
있다는 증거를 정리했다
([논문 서지 및 원문](https://deepblue.lib.umich.edu/items/c810051d-bb3a-48c7-86ae-da8ef48caa77)).
이 연구를 모든 취향 설명이 틀렸다는 뜻으로 확대하면 안 되지만, 말만으로 선택
메커니즘을 복원한다는 가정에는 근거가 약하다.

**[추론]** “나는 미니멀한 것을 좋아한다”고 말한 사람이 실제로는 높은 정보
밀도와 강한 상태 대비를 계속 고를 수 있다. 에이전트가 녹취를 매끄럽게 요약하면
이 모순이 사라지는 것이 아니라 더 그럴듯하게 숨는다. 따라서 말은 **가설**이고,
실제 A/B 선택이 반증 자료다.

### 2-2. 자유 대화는 추상 형용사를 과대표집한다

“차분한”, “대담한”, “신뢰감 있는”, “프리미엄”은 쉽게 말할 수 있지만 서로
다른 사람에게 다른 화면을 뜻한다. 녹취 요약기는 중복을 없애면서 이런 단어의
조건과 예외를 함께 지우기 쉽다. 영상 제작자가 “왜 그게 괜찮았는지 말로 쓰는
것이 제일 힘들었다”고 한 문제는 받아쓰기 정확도가 아니라 **판별 어휘와
대조군의 부재**다.

### 2-3. 참여자가 한 명이면 소유자 취향과 제품 진실이 섞인다

**[확인]** 2025년 DesignPref preprint는 20명의 전문 디자이너가 12,000개의
UI pairwise 비교를 수행했는데, binary preference의 Krippendorff's alpha가
0.25였다고 보고한다. 훈련된 디자이너 사이에도 선호 차이가 크고, 집계된
다수결이 개인 선호를 정확히 나타내지 않을 수 있다는 결과다
([DesignPref](https://arxiv.org/abs/2511.20513)). 이는 동료심사를 마친 확정
일반 법칙이 아니라 **preprint의 해당 실험 결과**로 제한해 해석한다.

**[제안]** 한 명의 founder/owner가 브랜드 취향의 정당한 최종 결정자일 수는
있다. 그 경우 단일 참여는 결함이 아니라 governance 선택이다. 다만 문서에는
“owner preference”라고 출처를 표시해야 하며, 이를 사용자 선호나 팀 합의로
표현하면 안 된다. 팀 제품이라면 최소한 decision owner, 실무 제작자, 목표
사용자의 입력을 서로 다른 열로 기록한다.

### 2-4. 취향이 아직 형성되지 않았으면 인터뷰가 취향을 발명한다

참여자가 아직 보지 못한 선택지에 대해 답하도록 하면 먼저 나온 예시, 질문의
표현, 인터뷰어의 추천이 기준점을 만든다. 이때 녹음은 “원래 있던 철학”을
발견한 기록이 아니라 그 자리에서 공동 생성한 철학의 기록이다. 공동 생성도
유효하지만, 발견된 사실처럼 쓰면 안 된다.

**[제안]** 답이 자주 바뀌거나 “둘 다”가 많으면 억지로 원칙을 확정하지 말고
`unsettled`로 남긴다. 먼저 다양한 실제 산출물을 작은 비용으로 경험하고,
선택 기록이 쌓인 뒤 문서에 승격한다.

### 2-5. 녹음에는 결정의 계보와 반증 조건이 없다

요약된 문장은 누가, 어떤 시안을 보고, 어떤 대안 대신, 어떤 제약 아래에서
말했는지 잃기 쉽다. 이후 에이전트는 “왜”를 검증할 수 없고, 문장이 바뀌어도
drift를 감지하기 어렵다. 문서에 원칙만 두지 말고 각 핵심 원칙에
`evidence`, `counterexample`, `owner`, `last validated`를 연결해야 하는 이유다.

## 3. 대안 프로토콜 세 가지

### 비교

아래 비용은 **[제안한 운영 범위]**이지 연구로 검증된 보편 수치가 아니다.

| 프로토콜 | 적합한 시작 상태 | 입력 비용 | 산출물 신뢰도 | 주된 실패 |
|---|---|---:|---|---|
| A. 기존 산출물에서 역추출 | 이미 제품·문서·선택 이력이 있음 | 낮음~중간 | 행동 증거에는 높음 | 기존 산출물이 우연·제약의 결과일 수 있음 |
| B. 구조화 인터뷰 + A/B + 반례 | 취향 가설은 있으나 문서가 없음 | 중간 | 현재 선택 재현에는 중간~높음 | 제시한 선택지 밖의 취향을 못 봄 |
| C. 디자인 일지 + 반복 토너먼트 | 취향이 아직 형성 중이거나 팀이 불일치 | 높음 | 시간에 걸친 안정성에는 가장 높음 | 느리고 후보 생성 품질에 영향받음 |

### A. 기존 산출물에서 역추출

1. 최근 실제 산출물 5~10개와 폐기한 산출물, 수정 요청, 최종 선택본을 모은다.
2. 반복되는 결정만 추출한다. 색 자체보다 “경고 외에는 고채도 색을 지웠다”,
   “표보다 설명을 먼저 놓았다” 같은 전후 차이를 우선한다.
3. 각 가설에 증거 파일과 결정자를 연결한다.
4. 충돌 사례를 찾고, 규칙이 아니라 상황 의존 결정인지 구분한다.
5. 사람에게 “이것이 의도인가, 우연인가, 당시 제약인가”만 확인한다.

장점은 기억이나 자기 설명보다 실제 행동을 먼저 본다는 것이다. 단, 현재
산출물이 legacy framework나 고객 요구에 묶여 있었다면 과거의 타협을 철학으로
오인할 수 있다. 그래서 최종 확인 인터뷰가 필요하다.

### B. 구조화 인터뷰 + A/B 강제 선택 + 반례 수집 — 기본 권고

#### 1단계: 사실 인터뷰

자유로운 “어떤 느낌을 원하세요?” 대신 다음 순서로 한 질문씩 묻는다.

1. 이 제품/문서를 쓰기 전과 후에 사용자의 행동이 어떻게 달라져야 하는가?
2. 가장 어려운 사용 상황은 무엇이며, 그때 무엇이 먼저 보여야 하는가?
3. 정확성, 속도, 친근함, 권위, 탐색성, 밀도 중 충돌하면 무엇이 우선하는가?
4. 절대 희생할 수 없는 것은 무엇인가?
5. 경쟁 대안과 같아 보여도 되는 부분과 달라야 하는 부분은 무엇인가?
6. 최근 “우리답다”고 승인한 결과와 “우리답지 않다”고 되돌린 결과는 무엇인가?
7. 최종 결정자는 누구이고 누구의 반대가 hard veto인가?
8. 6개월 뒤 이 철학이 실패했다고 판단할 관찰은 무엇인가?

답은 즉시 철학 문장으로 미화하지 않는다. `fact`, `preference`, `hypothesis`,
`unsettled`로 분류한다.

#### 2단계: 통제된 A/B

- 한 번에 한 축을 가능한 한 분리한다: 밀도, 위계, 대비, 타이포 리듬, 표면
  깊이, 장식량, 모션 강도 등.
- “A가 좋은가?”가 아니라 “이 사용 상황에서는 A와 B 중 어느 쪽이 더 맞는가?”를
  묻는다.
- 선택 뒤에 먼저 자유 설명을 받고, 그 다음 구조화 이유
  (`hierarchy`, `legibility`, `trust`, `distinctiveness`, `calm`, `other`)를 고른다.
- 순서 효과를 줄이기 위해 좌우 배치를 바꾸고, 일부 비교를 나중에 반복한다.
- 확신도와 “둘 다 부적합”을 허용한다. 강제 선택은 상대 선호를 얻기 위한
  장치이지 부적합한 후보를 승인시키는 장치가 아니다.

Pairwise preference elicitation은 낮은 인지 부담과 noise robustness를 주요
요건으로 다루는 선행 연구가 있다
([Guo & Sanner, 2010](https://proceedings.mlr.press/v9/guo10b.html)). 다만 이
연구가 Forma의 시각 취향 프로토콜을 직접 검증한 것은 아니다.

#### 3단계: 반례

좋아하는 것만 모으면 유행·브랜드 명성·콘텐츠 품질이 시각 선호와 섞인다.
다음 세 종류를 반드시 받는다.

- 보기에는 좋지만 우리 제품에는 맞지 않는 것
- 업계에서는 흔하지만 절대 따라 하고 싶지 않은 것
- 원칙상 맞아 보이지만 실제 시안에서는 싫었던 것

반례에는 싫다는 말뿐 아니라 **어떤 조건에서 예외가 가능한지**도 적는다.
현재 Forma 루트 `DESIGN.md`의 banned patterns가 좋은 출발 사례지만, 금지
목록만으로 원하는 방향을 생성할 수는 없다.

#### 4단계: 두 문서로 컴파일

에이전트가 초안을 쓰고 사람은 문장별로 `accept / revise / unsettled`를
표시한다. 녹음이 있다면 이때 누락 확인에만 사용한다. 원문 전체를 최종
컨텍스트에 넣지 않는다.

### C. 디자인 일지 + 반복 토너먼트

취향이 형성되지 않았거나 이해관계자가 합의하지 못하면 한 번의 workshop으로
끝내지 않는다.

1. 각 라운드의 후보 ID, 선택, 이유, 확신도, 결정자, 날짜를 로컬 기록으로 남긴다.
2. 다음 라운드는 가장 불확실하거나 서로 충돌한 축을 비교한다.
3. 2~3회 반복해서 살아남은 결정만 `DESIGN.md` 원칙으로 승격한다.
4. 제품 목표나 사용자 결과에 관한 결정은 별도로 `SOUL.md`에 승격한다.
5. 이전 결정을 뒤집으면 잘못으로 숨기지 말고 변경 이유와 적용 버전을 남긴다.

이 방법은 입력 비용이 가장 크지만 “취향을 아직 모른다”는 현실을 정직하게
다룬다. 현재 Forma 후보 UI와 평점 저장 경로는 아직 없으므로, 이 프로토콜의
자동화는 **[미확인/미구현]**이다.

### 권장 조합

- 기존 산출물이 있으면 **A → B의 짧은 확인 → 보류 A/B 검증**.
- 처음 만드는 제품이면 **B → C의 2~3개 라운드 → 보류 A/B 검증**.
- 녹음은 B의 인터뷰를 편하게 하는 선택 사항이다. STT나 외부 요약 서비스를
  Forma가 붙이는 것은 현재 외부 LLM/문서 전송 금지와 충돌할 수 있으므로 이번
  권고에 포함하지 않는다.

## 4. 기존 Forma 인터뷰 도구를 재사용할 수 있는가

### 저장소 안에서 확인한 것

**[확인]** `skills-src/forma/instructions.md`에는 artifact와 variant를 먼저
제안하고, 선택 이유·포함/제외 범위·가까운 대안을 짧게 설명한 뒤 사용자의
승인을 기다리는 “propose, then agree” 절차가 있다. 이는 잘못된 artifact
선택을 막는 **단일 decision gate**이지, 취향을 여러 증거로 elicitation하는
인터뷰 스킬은 아니다. 저장소의 `skills-src`, `docs`, `src`에서 interview
전용 파일이나 구현은 검색되지 않았다.

**[확인]** 사용자 환경의 `grill-me`/`grilling` 스킬은 한 번에 질문 하나,
각 질문에 추천 답 제시, 코드에서 확인 가능한 것은 묻지 말고 탐색한다는 규칙을
갖는다. `requirements-grill`도 한 질문씩 진행하고 background, user contract,
internal invariant, verification requirement 등을 분리한다. 그러나 둘 다 계획·
요구사항을 정련하는 도구이며 시각 선호 A/B, 반례, 반복 일관성, evidence
provenance를 다루지 않는다.

### 재사용 판단

**[제안]** 다음 부분만 재사용한다.

- 한 번에 질문 하나
- 질문마다 추천안을 주되 추천이 선택을 오염시킬 수 있음을 표시
- 저장소/기존 산출물에서 답을 찾을 수 있으면 사람에게 다시 묻지 않음
- 합의된 결정과 미합의를 분리
- 최종 문서 위치와 검증 기준까지 확인

다음은 새로 필요하다.

- 시각 후보를 같은 조건에서 보여 주는 pairwise UI 또는 정적 review pack
- 좌우 순서 무작위화, holdout pair, 반복 pair
- 선택 이유 코드와 자유 설명의 동시 저장
- 반례와 evidence 링크
- `SOUL`/`DESIGN` 분류 규칙

따라서 기존 grill을 그대로 이름만 바꿔 쓰는 것보다, 그 대화 규칙을 가져온
`design-direction-interview` 성격의 별도 프로토콜이 맞다. 이번 과제는 조사
문서만 작성하므로 실제 스킬 생성은 하지 않는다.

## 5. 두 파일의 역할과 경계

### 권장 역할

| 항목 | `.forma/SOUL.md` | `.forma/DESIGN.md` |
|---|---|---|
| 핵심 질문 | 우리는 누구를 위해 어떤 판단을 우선하는가? | 그 판단은 어떤 시각 규칙으로 드러나는가? |
| 내용 | 제품 목적, 대상과 맥락, 가치 우선순위, 경험 약속, trade-off, 비목표, 의사결정권 | 정보 위계, 밀도, 타이포, 색 역할, 표면, 리듬, motion 의미, do/don't, artifact별 변주 |
| 변경 속도 | 느림 | 중간; 검증된 라운드마다 변경 가능 |
| 읽는 주체 | 사람과 에이전트 | 사람과 에이전트; 향후 compiler의 근거 |
| renderer 직접 입력 | 아님 | 아님; 승인된 결정은 별도 typed profile로 투영 |
| 금지 | hex, CSS selector, 특정 컴포넌트 값 | 제품 mission의 재서술, 일회성 캠페인 목표 |

1단계의 “DESIGN=시각 언어, SOUL=제품 철학” 구분은 맞다. 다만 경계는 다음
상황에서 모호해진다.

| 모호한 표현 | SOUL에 남길 부분 | DESIGN으로 내릴 부분 |
|---|---|---|
| “신뢰감을 준다” | 왜 신뢰가 중요한지, 무엇을 숨기지 않는지 | 근거·상태·출처를 먼저 보이는 위계, 장식보다 대비를 상태에 사용 |
| “차분하다” | 고압 상황에서 판단 부담을 낮춘다는 경험 목표 | 채도, 밀도, 모션, 여백의 판정 규칙 |
| “전문가답다” | 대상 사용자의 숙련도를 존중하고 정보를 생략하지 않음 | 전문 용어 표시 방식, 밀도와 설명의 균형, 타이포 리듬 |
| “접근성 우선” | 포용성이 trade-off에서 우선한다는 가치 | 대비, focus, reduced motion 등 구체 불변 조건 |
| “distinctive” | 경쟁 대안과 달라야 하는 이유 | 반복되는 signature element와 금지되는 generic pattern |

좋은 경계 검사 질문은 간단하다.

- 시각 표현이 전혀 달라져도 문장이 여전히 참이면 `SOUL.md`다.
- 제품 목적이 같아도 구현 매체에 따라 문장이 달라지면 `DESIGN.md`다.
- 값·타입·alias가 필요하면 Markdown이 아니라 기계용 token/profile 후보다.

### 파일 위치와 이름 충돌

**[확인]** Forma 저장소 루트 `DESIGN.md`는 Forma 자체 visual language의 single
source of truth다. `AGENTS.md`도 이를 명시하며, 파일은 토큰, layout grammar,
금지 패턴, artifact 방향, 접근성·오프라인 불변 조건을 설명한다.

**[제안]** Forma로 문서를 만드는 사용자의 파일은 **그 사용자 프로젝트의
`.forma/SOUL.md`와 `.forma/DESIGN.md`**에 둔다.

```text
user-project/
├── .forma/
│   ├── SOUL.md       # 제품 철학과 trade-off
│   ├── DESIGN.md     # 프로젝트 시각 언어와 예/반례
│   └── design.tokens.json  # 향후: 검증 가능한 renderer 입력
├── forma.spec.json
└── ...
```

이 위치는 다음 장점이 있다.

- Forma engine의 루트 `DESIGN.md`와 물리적으로 충돌하지 않는다.
- 두 문서가 일반 개발 agent 지침인 `AGENTS.md`/`CLAUDE.md`로 오인되지 않는다.
- 프로젝트마다 하나라는 스코프가 명확하다.
- 향후 review 기록과 token profile을 같은 제품 경계 아래 둘 수 있다.

**[미확인]** 현재 CLI에는 `.forma/` 프로젝트 설정 discovery가 없고, 이 경로를
읽는 구현도 없다. 따라서 이는 위치 권고이지 현재 동작 설명이 아니다. 또한
외부 프로젝트의 profile을 렌더 시 암묵적으로 읽으면 spec 자기완결성이 깨진다.
권장 해결은 render 전에 profile을 검증하고 선택 값을 spec 또는 manifest에
스탬프해 같은 입력이 다른 작업 디렉터리에서도 같은 결과를 내게 하는 것이다.

### 문서별 예외

프로젝트마다 하나가 기본이지만, 문서 목적상 다른 표현이 필요한 경우가 있다.
그때 `DESIGN.md`를 복제하지 않는다.

- `DESIGN.md`는 허용된 변주 범위와 artifact별 방향을 정의한다.
- `forma.spec.json`은 그 범위 안의 variant/composition 선택만 기록한다.
- 범위 밖 예외는 임시 override가 아니라 `DESIGN.md` 개정 또는 별도 브랜드
  profile로 명시 승인한다.

## 7. 잘 만들어졌는지 어떻게 검증할 것인가

### 단일한 “정답 검사”는 없다

취향 문서에는 외부의 유일한 정답이 없다. 한 사람의 일관된 취향이 목표 사용자
성과에는 나쁠 수 있고, 사용자에게 좋은 결과가 브랜드 owner에게는 “우리답지
않게” 보일 수 있다. 따라서 검증 대상을 분리한다.

1. 문서가 내부적으로 명확하고 실행 가능한가
2. 에이전트가 문서를 읽고 동일한 판단을 재현하는가
3. 문서가 decision owner의 아직 보지 않은 선택을 예측하는가
4. 그 선택이 목표 사용자의 실제 결과를 개선하는가

1~3이 통과해도 4를 보장하지 않는다.

### 검증 계층

| 검사 | 방법 | 잡는 것 | 놓치는 것 |
|---|---|---|---|
| 구조 lint | 필수 절, owner, scope, evidence, counterexample, `unsettled` 여부 검사 | 누락, 무주체 원칙, 모호한 완결 흉내 | 철학의 타당성 |
| 모순/우선순위 검사 | 같은 상황에서 충돌하는 규칙과 승자 규칙 확인 | “minimal”과 “dense” 같은 무해결 충돌 | 실제 선택에서의 일관성 |
| traceability | 핵심 원칙을 인터뷰 문답·기존 산출물·선택 기록에 연결 | 근거 없는 요약, 출처 drift | 근거 자체가 편향됐는지 |
| agent comprehension probe | 같은 brief로 여러 번 분류·선택하게 하고 이유와 문서 절을 요구 | 에이전트가 다르게 해석하는 문장 | 결과의 시각 품질, 사용자 적합성 |
| holdout pair test | 문서 작성에 쓰지 않은 A/B에서 문서의 예측과 owner 선택 비교 | stated/revealed preference 불일치, 과적합 | 새 스타일·새 맥락으로의 일반화 |
| repeated pair test | 시간 간격 후 일부 pair 재제시 | 선택 안정성, 미형성 취향 | 어느 선택이 더 좋은지 |
| stakeholder split | owner/제작자/사용자 결과를 별도 집계 | 숨은 불일치, 가짜 합의 | 최종 governance 결정 |
| task outcome test | 실제 독자의 탐색 시간, 오류, 이해, 완료율 등 측정 | 철학이 사용자 목적에 기여하는지 | 브랜드 소유자의 미적 만족 |

### 최소 수용 기준 — 제안

다음은 객관적 업계 표준이 아니라 Forma 도입 실험을 위한 **[제안 기준]**이다.

- 각 핵심 원칙이 최소 하나의 판정 규칙 또는 반례를 가진다.
- `SOUL`과 `DESIGN`에 같은 문장이 중복되지 않고, 링크로 연결된다.
- hard constraint와 취향이 충돌할 때 hard constraint가 우선한다고 명시한다.
- 보류 A/B에서 문서가 선택 이유를 설명하지 못한 항목은 `unsettled`로 되돌린다.
- 서로 다른 에이전트/세션이 같은 입력에서 정반대의 결론을 내리면 문장을
  더 구체화한다. 합의율 숫자를 품질 점수로 숭배하지 않는다.
- 목표 사용자의 결과를 주장하려면 실제 사용자 검사나 직접 근거가 있어야 한다.
  owner 인터뷰만으로 “사용자가 신뢰한다”고 쓰지 않는다.

## 8. Forma에 적용할 때의 권장 순서

이 문서의 범위는 저작 방법 조사이며 구현 계획은 아니다. 그래도 선후 관계는
다음처럼 고정할 수 있다.

1. **문서 계약부터 정한다.** `.forma/SOUL.md`와 `.forma/DESIGN.md`의 역할,
   provenance, `unsettled`, governance를 정의한다.
2. **수동 프로토콜로 2~3개 실제 프로젝트를 수행한다.** 자동화를 만들기 전에
   A/B와 반례가 실제로 더 유용한 원칙을 만드는지 확인한다.
3. **보류 pair로 예측력을 본다.** 인터뷰에 쓰인 같은 예시를 다시 보여 주고
   “맞았다”고 하지 않는다.
4. **그 다음 typed design profile을 설계한다.** DTCG 형식을 참고하되 Forma가
   필요한 축만 정의한다.
5. **1단계 병목인 renderer 통로를 연다.** `buildStylesheet`, `artifactCss`,
   `blockCss`가 검증된 profile을 받도록 하되 최종 spec의 재현성을 보존한다.
6. **후보 review를 자동화한다.** hard gate와 취향 평가는 계속 별도 열로 둔다.

## 남은 불확실성

1. `.forma/DESIGN.md`에서 typed profile로 투영할 정확한 schema와, DTCG
   2025.10의 어느 subset을 채택할지는 미확인이다.
2. profile 값을 spec/manifest에 어떻게 고정해야 현재의 자기완결적 재현성을
   유지하는지 설계가 필요하다.
3. pairwise 후보의 축을 어떻게 직교에 가깝게 만들지, 한 라운드의 적정 비교
   수가 얼마인지는 사용자 실험 없이 확정할 수 없다.
4. DesignPref는 유용한 최신 근거지만 preprint이며, Forma의 문서 디자인과
   동일한 과업이 아니다.
5. 한 명의 owner 취향을 우선할지 여러 stakeholder 합의를 우선할지는 도구가
   결정할 문제가 아니라 프로젝트 governance 입력이다.
6. 현재 Forma 저장소에는 전용 design-direction interview 스킬, `.forma/`
   discovery, preference 기록 schema가 없다.

최종적으로 영상의 핵심인 “철학은 사람이 준다”는 유지한다. 다만 사람은 철학을
완성된 문장으로 한 번에 제공하지 않는다. 사람은 목표, 과거 선택, A/B 판단,
싫은 사례, 충돌 시 우선순위를 제공하고, 에이전트는 그것을 출처와 불확실성을
보존한 문서로 컴파일한다. 녹음은 이 과정의 편리한 메모 방식이지 진실 판별
장치가 아니다.
